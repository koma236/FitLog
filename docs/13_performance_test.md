# 15. パフォーマンステスト

> 壁打ち用の草案。未承認・未実装・独立レビュー未実施。数値・方式は提案であり、実行結果ではない。

### 15.1 位置づけ
MyTimelineと同じく負荷試験の設計・結果を独立文書にする。低費用デモの容量を説明できることを目的とし、大規模SNSの性能を主張しない。

### 15.2 ツールと環境
k6を候補とする。まずローカルの隔離DB・S3互換環境で固定seedを使用。AWS負荷試験は費用とスコープを別途示す。アプリの品質checksと同一環境で並行実行しない。

### 15.3 仮の合否基準
利用者5名、投稿1,000件、各投稿最大10種目×20セットという境界ケースと通常ケースを分ける。ウォームアップ後5分間、通常APIのp95<1秒、5xx<1%を仮目標。画像uploadは別シナリオで容量・転送時間も記録。

### 15.4 認証の扱い
各仮想利用者が自分のセッションとCSRFを持つ。Cookieを全ユーザーで共有しない。認証集中と通常アクセスを分ける。

### 15.5 テスト種別
smoke→通常loadの順。stress/spike/soakは必要性を判断し別実施。費用・時間・データ量を無制限にしない。

### 15.6 確かめたい懸念
投稿ごとの種目・セット・いいね件数・フォロー状態によるN+1、カーソルの安定性、画像decodeのCPU・メモリ、同時いいねの一意制約、検索の走査範囲。

### 15.7 結果の記録
commit、日時、依存版、環境、データ量、負荷、p50/p95/p99、エラー率、CPU/メモリ、費用・実行時間を記録。現時点は設計のみで合格結果はない。
